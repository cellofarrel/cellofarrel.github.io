Introduction: The Challenge

the objective of this was not merely to write code, but to engineer a system that mimics real-world chaos. I built MemeScale, a resource-intensive meme generator service. The true test lay in "operations": observing the system's behavior when pushed to its breaking point.

This report documents the entire lifecycle: from the architectural decisions, to the brutal stress testing using k6, and finally, a strategic roadmap for scaling.

01

System Architecture

Designing for Observability and Isolation

The architecture adheres to the Microservices-Ready pattern. Although currently deployed as a cohesive unit, the components are loosely coupled to allow for independent scaling in the future.

The Application Stack

  • Frontend & Backend (Unified Flask) A Python Flask application serving both the UI (Jinja2) and the API. It utilizes the Pillow library for image manipulation—a deliberately CPU-heavy task chosen to simulate computational bottlenecks.
  • Persistence (PostgreSQL) Relational database storing generation metadata (Timestamp, Text Content, File Size). Chosen for ACID compliance and strictly isolated from public access via Docker networks.

The Observability Stack

  • Prometheus (Scraper) configured to scrape the /metrics endpoint of the Flask app every 15 seconds. It stores time-series data of our custom instrumentation.
  • Grafana (Visualizer) Connected to Prometheus as a data source. Custom dashboards were built to correlate CPU spikes with Latency degradation.

Deployment Strategy

The system is containerized using Docker and orchestrated via Docker Compose. This ensures environment consistency (Infrastructure as Code). Crucially, I implemented a private monitoring network to ensure that the database and Prometheus are not exposed to the host machine's public interface, adhering to security best practices.

Selected based on the Google SRE "Four Golden Signals" framework.

Load Simulation Strategy

Methodology and Scenario Design using k6

To validate the architecture, I utilized k6, a modern load testing tool tailored for developer-centric performance testing. The test was designed to simulate two distinct traffic patterns to establish a baseline and then find the breaking point.

script.js (k6 Configuration) 
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  // Scenario 1 & 2 defined via stages
  stages: [
    { duration: '30s', target: 20 },  // 1. Normal Load (Warmup)
    { duration: '1m', target: 200 },  // 2. High Load (Spike to 200 VU)
    { duration: '30s', target: 0 },   // 3. Cooldown
  ],
  thresholds: {
    http_req_duration: ['p(95)<2000'], // Fail test if latency > 2s
  },
};

export default function () {
  // Test the heavy endpoint
  const payload = { text: "EXAM STRESS", image: http.file(binFile, 'test.jpg') };
  const res = http.post('http://localhost:5000/generate', payload);
  
  check(res, { 'status was 200': (r) => r.status == 200 });
  sleep(1);
}

Scenario A: Normal Load

  • Users: 20 Concurrent VUs
  • Duration: 30 Seconds
  • Goal: Establish baseline latency and ensure DB connectivity is stable.

Scenario B: High Load (Stress)

  • Users: Ramp up to 200 Concurrent VUs
  • Duration: 1 Minute
  • Goal: Force CPU saturation and identify the maximum throughput (RPS) before degradation.

Analysis & Diagnostics

The "Success" that felt like a Failure

The "12-Second Paradox"

The simulation results (shown in the attached evidence) reveal a critical insight. The system achieved a 0.00% Error Rate (all 2010 requests returned HTTP 200). However, the p95 Latency reached 12.01 seconds. Technically, the system worked. Functionally, it was unusable.

Root Cause Analysis (Forensics)

1. Synchronous Blocking (The GIL)

The Application is running a blocking operation (Image Processing) on the main thread. Python's Global Interpreter Lock (GIL) prevents true parallelism in a single process. With 200 users trying to generate memes, requests form a queue. The 200th user has to wait for previous images to finish, resulting in the massive 12s wait time.

2. Connection Backpressure

Since the CPU was at 100%, the application couldn't accept new TCP connections fast enough. However, the PostgreSQL latency remained low (8ms). This confirms that the database was not the bottleneck. The bottleneck was purely computational within the Flask container.

Required Additional Metrics

  • Queue Depth (Gunicorn/uWSGI): To see exactly how many requests are waiting in the socket backlog.
  • Context Switches: To verify if the OS is thrashing between threads trying to get CPU time.

Incident Response Playbook

Trigger: Latency > 2s

  1. Alerting: PagerDuty notifies on-call engineer via Grafana Webhook.
  2. Triage: Check "CPU Usage" panel. If 100%, confirm scaling issue.
  3. Mitigation: Execute docker compose up -d --scale meme-app=5 to immediately add 4 more workers.
  4. Resolution: Monitor Latency drop. Post-mortem analysis.
04

Evaluation & Roadmap

From Prototype to Production-Grade

Evaluation: What went right?

Database Isolation: Because the DB was in a separate container/network, the CPU crash of the app did not corrupt the database state.

Zero Data Loss: Despite high latency, the error rate was 0%. The retry mechanisms and timeout buffers held up.

Strategic Improvements

To solve the "12-second paradox" and align with Performance, Cost, and Sustainability goals:

1

Asynchronous Processing (Celery + Redis)

The Change: Decouple the HTTP request from the image generation. The API returns "202 Accepted" immediately. A background worker (Celery) processes the queue.

Impact: Latency drops from 12s to 50ms.
Cost: Adds Redis cost, but reduces API server size.
Metric: Queue Length.
2

Intelligent Caching (Redis)

The Change: Hash the requested text ("EXAM STRESS"). If the image exists in Redis, serve the binary directly without using CPU.

Sustainability: Reduces CPU cycles (Carbon footprint) by 60%.
Performance: Near-instant retrieval.
Metric: Cache Hit Rate.
3

Autoscaling (Kubernetes HPA)

The Change: Migrate to K8s. Configure Horizontal Pod Autoscaler (HPA) to spawn pods when CPU > 70%.

Reliability: Eliminates the 12s queue buildup.
Cost: Scale down to 1 pod at night (Cost efficiency).
Metric: Replica Count.
